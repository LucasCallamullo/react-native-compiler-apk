Propuesta de cambio Módulo Files

Agregar enum TypeFile a StoredFile

Separar el tipo lógico del archivo (audio, imagen, video, texto) del MIME técnico para habilitar filtrados, validaciones y consumo desde otros módulos.

Situación actual

Hoy StoredFile solo guarda el MIME técnico (contentType):

@Column(nullable = false)
private String contentType; // "image/png", "audio/mpeg", "application/pdf"

Problema: el MIME es un string libre. Cada vez que un módulo quiere saber "¿esto es una imagen?" tiene que parsear el string, hacer startsWith("image/"), o mantener una lista de MIMEs permitidos. Eso es frágil y se repite en varios lugares.

Propuesta

Agregar un campo typeFile tipado como enum, que clasifique el archivo a alto nivel:

public enum TypeFile {
    AUDIO,
    IMAGE,
    VIDEO,
    TEXT,
    DOCUMENT,   // pdf, docx, xlsx
    OTHER       // fallback para tipos no clasificados
}

El MIME (contentType) se sigue guardando para precisión técnica. El enum typeFile se agrega como capa de clasificación lógica.

Ventaja: los módulos consumidores ya no parsean strings. Preguntan file.getTypeFile() == TypeFile.IMAGE y listo.

Entidad actualizada 

@Entity
@Table(name = "stored_files")
@Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder
public class StoredFile {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String originalName;

    @Column(nullable = false, unique = true)
    private String storedName;

    @Column(nullable = false)
    private String contentType;    // MIME técnico

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private TypeFile typeFile;     // NUEVO — clasificación lógica

    @Column(nullable = false)
    private long size;

    @Column(nullable = false)
    private String relativePath;

    @Column(nullable = false)
    private Instant uploadedAt;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "user_id", nullable = false)
    private User user;
}

Nota: @Enumerated(EnumType.STRING) guarda el nombre del enum como texto ("IMAGE"), no como ordinal. Esto es más legible en la DB y resiste reordenamientos del enum.

Utilidad por módulo

Filtrado de archivos

findByUserAndTypeFile(user, IMAGE) en vez de findByContentTypeStartingWith("image/"). Una query, un índice, cero parseo.

Módulo ShareLink

El campo fileTypes del link de compartir puede referenciar directamente TypeFile. Sin esto, tendrías que guardar MIMEs sueltos y mapearlos a mano.

Validaciones

Reglas de negocio como "solo se pueden compartir AUDIO e IMAGE" se expresan contra el enum, no contra el MIME.

Mobile / UI

El front recibe "IMAGE" y decide icono, color y agrupación. No tiene que inferir nada desde un MIME.

Estadísticas / reportes

"¿Cuántas imágenes subió este usuario?" se resuelve con un COUNT sobre typeFile. Sin parseo ni LIKE.

Migración / purga

Políticas como "borrar videos después de 90 días" se aplican por tipo, no por MIME. El enum es la unidad de negocio.

Antes vs. Después

Sin enum

  • • Parsear contentType en cada módulo.
  • • Listas de MIMEs permitidos duplicadas.
  • • Queries con LIKE 'image/%'.
  • • Front adivina iconos desde strings.
  • • Nuevos formatos (ej. .webp) rompen lógica.

Con enum

  • • file.getTypeFile() == IMAGE directo.
  • • Enum único como fuente de verdad.
  • • Query por columna indexable.
  • • Front recibe categoría explícita.
  • • Nuevos formatos se mapean al enum en un solo lugar.

Cómo se puebla el campo

Al momento de subir un archivo, el servicio que persiste el StoredFile debe resolver el enum a partir del MIME. Ejemplo: 

public static TypeFile fromMimeType(String mime) {
    if (mime == null) return TypeFile.OTHER;
    if (mime.startsWith("image/"))    return TypeFile.IMAGE;
    if (mime.startsWith("audio/"))    return TypeFile.AUDIO;
    if (mime.startsWith("video/"))    return TypeFile.VIDEO;
    if (mime.startsWith("text/"))     return TypeFile.TEXT;
    if (mime.equals("application/pdf")
        || mime.contains("word")
        || mime.contains("excel")
        || mime.contains("spreadsheet")) return TypeFile.DOCUMENT;
    return TypeFile.OTHER;
}

Este mapeo vive en un solo lugar (el enum o un servicio utilitario). Si mañana se agrega un tipo nuevo, se toca una vez y todos los módulos lo ven.

Checklist de implementación

  • Crear enum TypeFile en com.vg.auth.model.utils (o donde vivan los enums).
  • Agregar campo typeFile a StoredFile con @Enumerated(EnumType.STRING).
  • Implementar el mapeo MIME → TypeFile (método estático o servicio).
  • Migración SQL: agregar columna type_file VARCHAR(20) NOT NULL y poblarla para filas existentes.
  • Actualizar el servicio de subida para setear typeFile al persistir.
  • Agregar método de repositorio findByUserAndTypeFile si hace falta.
  • Exponer typeFile en el DTO de respuesta de archivos.
