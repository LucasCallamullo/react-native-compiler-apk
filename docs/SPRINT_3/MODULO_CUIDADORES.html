Módulo Backend

Caregiver Links

Sistema de vinculación entre un usuario protegido y un cuidador de confianza mediante un código de invitación único.

Spring Boot JPA / Hibernate UUID como código Soft delete (status)

1 Contexto y objetivo

La app funciona como una bóveda digital que guarda capturas y archivos privados. Para compartir contenido de forma segura, el usuario puede designar cuidadores de confianza: otras personas registradas en la app que podrán recibir notificaciones y acceder a ciertos recursos.

Este módulo resuelve cómo se vincula un protegido con su cuidador sin exponer datos sensibles y sin requerir que el protegido conozca de antemano el email o teléfono del cuidador.

Idea central: el protegido genera un código (un UUID). Se lo pasa al cuidador por cualquier canal externo (WhatsApp, mail, en persona). El cuidador lo ingresa en la app y queda vinculado.

Nota: caregiver_id es nullable porque al crear el link todavía no existe cuidador. Se llena cuando alguien acepta el código.

3 Entidad CaregiverLink 

@Entity
@Table(name = "caregiver_links")
@Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder
public class CaregiverLink {

    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id; // este UUID ES el código de invitación

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "caregiver_id")
    private User caregiver; // null hasta que alguien acepta

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "protected_id", nullable = false)
    private User protectedUser; // siempre presente

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private CaregiverLinkStatus status; // PENDING, ACCEPTED, REVOKED

    @CreationTimestamp
    @Column(name = "created_at", updatable = false)
    private LocalDateTime createdAt;

    @Column(name = "accepted_at")
    private LocalDateTime acceptedAt;

    @Column(name = "revoked_at")
    private LocalDateTime revokedAt;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "revoked_by")
    private User revokedBy;
}

Explicación campo por campo

Campo Por qué existe
id (UUID) Es a la vez PK y código de invitación. Un UUID es imposible de adivinar, no necesita hashing extra y no colisiona.
protectedUser El usuario que genera el código. Siempre presente desde el momento de la creación.
caregiver Nullable. Se llena cuando otro usuario ingresa el código y acepta. Hasta entonces, el link está "esperando".
status Máquina de estados: PENDING → ACCEPTED → REVOKED. Nunca se borra la fila.
acceptedAt Auditoría: cuándo se vinculó el cuidador.
revokedAt / revokedBy Auditoría de revocación. revokedBy permite saber si revocó el protegido o el sistema.

4 Flujo paso a paso

PASO 1

El protegido genera el código

El usuario autenticado crea una invitación. El sistema devuelve el UUID que deberá compartir.

POST /api/caregiver-links

→ Crea CaregiverLink {
    id: UUID generado,
    protectedUser: usuario autenticado,
    caregiver: null,
    status: PENDING,
    createdAt: now()
  }
→ Devuelve: { "code": "a3f8-..." }
PASO 2

El cuidador acepta el código

Otro usuario (con cuenta propia) ingresa el código en la app. El sistema valida y vincula.

POST /api/caregiver-links/{code}/accept

→ Busca link por id = code y status = PENDING
→ Si no existe o no está PENDING → 404 / 409
→ Asigna caregiver = usuario autenticado
→ Asigna rol CAREGIVER al usuario (si no lo tiene)
→ status = ACCEPTED, acceptedAt = now()
PASO 3

El protegido revoca (opcional)

En cualquier momento, el protegido puede desvincular al cuidador. No se borra, se marca como revocado.

PATCH /api/caregiver-links/{id}/revoke

→ Verifica que el solicitante sea el protectedUser
→ status = REVOKED, revokedAt = now(), revokedBy = solicitante
→ (Opcional) Quitar rol CAREGIVER si ya no cuida a nadie más

5 Endpoints del módulo

Método Endpoint Acción Quién
POST /api/caregiver-links Generar código Protegido
POST /api/caregiver-links/{code}/accept Aceptar invitación Cuidador
PATCH /api/caregiver-links/{id}/revoke Revocar vínculo Protegido
GET /api/caregiver-links Listar mis cuidadores Protegido
GET /api/caregiver-links/caring Listar a quiénes cuido Cuidador

Nota sobre POST vs PUT: accept y revoke son acciones, no reemplazos de recurso. Por eso van como POST o PATCH, nunca PUT.

6 Decisiones de diseño

🔑 El UUID es el código

No hace falta un campo extra. Un UUID v4 tiene 122 bits de entropía, es imposible de adivinar y no colisiona. El id cumple doble función: PK e invitación.

🗑️ Nunca borrar, solo cambiar estado

La fila se conserva con status = REVOKED. Tenés historial completo de quién cuidó a quién y cuándo. Es auditoría gratis.

👤 caregiver nullable

Al crear el link todavía no hay cuidador. Solo el protegido. El campo se llena en el paso 2. Esto permite tener códigos "flotando" sin usar.

🎭 Rol + tabla, no uno solo

La tabla dice a quién cuida. El rol CAREGIVER dice qué puede hacer. Son cosas distintas. A futuro vas a querer @PreAuthorize("hasRole('CAREGIVER')").

📜 revokedBy para auditoría

Permite saber si revocó el protegido o el sistema (por ejemplo, si se eliminó la cuenta del cuidador). Sin esto, perdés trazabilidad.

🚫 No mezclar con Contact

Contact es una libreta externa (gente sin app). CaregiverLink es entre usuarios registrados. Son conceptos distintos y no se cruzan.
